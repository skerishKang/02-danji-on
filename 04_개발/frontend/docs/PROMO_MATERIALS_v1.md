# 단지온 현장시연 홍보물 3종 계약 v1

## 목적

Google Drive `단지온_8월현장시연_통합시제품_v1` Scene 06의 홍보물 만들기 흐름을 제품 코드에서 재현한다.

핵심 표현은 AI 생성이 아니라 **주민이 입력한 생활정보가 필요한 홍보 형식으로 정돈·편집되는 과정**이다.

## 입력

홍보물은 사용자가 별도 프롬프트를 작성하지 않는다. 이미 제출한 가게·서비스 신청의 다음 공개정보를 사용한다.

- 가게·서비스명
- 분야
- 한 줄 소개
- 가격
- 이용지역
- 주민혜택
- 주민관계
- 대표사진

정확한 동·호수, 주민 인증 증빙 원문 등 비공개 관계확인 자료는 홍보물 입력으로 사용하지 않는다.

## 출력

`홍보물 만들기`를 누르기 전 세 출력물은 대기상태다. 클릭 후 약 110ms 간격으로 다음 순서로 완성한다.

1. 단지온 가게소개 카드
2. 카카오톡 공유 이미지
3. 엘리베이터 게시판 포스터

현장시연 단계에서는 결과물을 브라우저 DOM으로 구성한다. 실제 PNG/JPG 파일 생성, 카카오톡 전송, 인쇄 API는 인프라 연결 이후 별도 구현한다.

## 대표사진 연속성

mock 환경에서도 등록 시 올린 대표사진을 홍보물 화면에서 다시 쓸 수 있어야 한다.

- application record: 기존처럼 `representativeImageObjectKey`만 저장
- mock binary: IndexedDB `danjion-mock-storage-v1/files`
- 홍보물 화면: `storageAdapter.resolvePreview(objectKey)`로 Blob을 다시 읽어 object URL 생성
- 페이지 종료: 생성한 object URL revoke
- 실제 사진이 없으면 PR #5에서 도입한 현장 작업사진 sprite를 업종별 fallback으로 사용

R2가 연결된 뒤에도 UI는 같은 storage adapter 경계를 사용한다.

## 신청 상태

홍보물 진입 대상:

- `pending`
- `approved`

`rejected` 신청은 홍보물 진입 대상으로 노출하지 않는다.

신청 상세 로드는 `dataAdapter.getMyBusinessApplication(applicationId)`를 사용해 현재 사용자 소유권 경계를 유지한다.

## 금지

- AI 반짝이
- 로봇 아이콘
- 프롬프트 입력창
- 의미 없는 생성 진행 애니메이션
- 이모지를 대표 시각물로 사용하는 홍보물
- 비공개 주민 인증자료의 홍보물 노출

## E2E 승인 조건

1. 4단계 등록에서 한결수학 시연정보 입력
2. 대표 이미지 업로드
3. 신청 완료
4. 내정보에서 홍보물 만들기 진입
5. 클릭 전 3종 대기
6. 클릭 후 3종 완성
7. 등록 대표사진이 세 출력물에 재사용
8. 세 출력물에 동일 신청정보가 반영
9. 대표사진 없는 신청은 실제 작업장면 fallback 사용
10. 로봇/반짝이 artwork 없음
11. built state에서 axe serious/critical 위반 0

## 상위 시연 순환

`발견 → 검색 → 주민 우선목록 → 상세 → 혜택 보관 → 내정보 → 4단계 등록 → 홍보물 3종 → 운영확인 → 승인 공개 → 공개 목록 재진입 → 생활경제 엔딩`

다음 단계는 Scene 07 운영확인이다. 공개정보와 비공개 주민관계 확인을 명시적으로 분리하며, 비공개 영역은 `확인자료 1건`처럼 존재만 표시하고 실제 동·호수나 문서 원문을 노출하지 않는다.
